热门商品先放手边：缓存怎样减少重复劳动

虚构小店的教学场景。规模、耗时和算例不是生产性能承诺；技术方案均需按实际部署核验。

  1. 数据库反复回答同一个问题，为什么不记下来？
  2. 命中与未命中：程序承担了哪些新工作
  3. 价格改了，缓存还没改：并发与一致性
  4. 选本机缓存还是 Redis，以及怎样保住系统

数据库反复回答同一个问题，为什么不记下来？

一次活动里，很多顾客反复查看同一款帆布包。名称、介绍和图片地址几分钟都不变，但每次都要数据库重新查。增加数据库规格可以承担更多工作，可这些工作中相当一部分只是重复回答同一个问题。

缓存就是把允许复用的结果暂存起来。程序下次先问“手边有没有”，有就使用，没有才去正式数据源查询。它适合减少重复读取，但不是把数据库永久搬到内存，更不是把所有数据都复制一份就完事。

内存缓存为什么可能快？

缓存常把结果放在内存，按事先设计的键定位，避免重复执行较复杂的查询与整理。但“使用内存”不等于没有成本：请求仍有网络、序列化、服务排队和数据复制。数据库也有内存缓冲，不能简单说数据库每次都读磁盘而 Redis 永远零等待。

收益取决于原查询成本、命中率、数据大小和网络环境。如果原查询很便宜、数据很少复用，加入缓存反而可能增加代码与网络调用。要测量，而不是因为大家用 Redis 就照装。

缓存键是给答案起一个准确名字

例如 product:123:public:v2 可以表示某商品公开展示数据的某版本结构。如果不同语言、币种或用户等级会得到不同内容，键或缓存策略就要区分这些条件。否则可能把错误价格或私人内容交给另一个顾客。

键不是越长越好，而是应包含决定结果的必要因素。缓存里保存的是展示副本还是最终交易依据，也必须提前说清楚。本章只缓存允许稍旧的公开展示信息。

命中与未命中：程序承担了哪些新工作

命中时，数据库这次可以休息

未命中不意味着 Redis 去查数据库

这种由应用在旁边管理缓存的方式常叫旁路缓存。它不是数据库原生复制；缓存与数据库更新并不天然同一个事务。

过期时间到底表示什么？

过期时间规定缓存值在某个时间后不再被当作有效内容。短一些通常更新鲜，但更多请求需要回数据库；长一些可能节省查询，却容忍更久旧数据。它不是商品本身的有效期，也不保证这段时间内数据库没有改变。

一次命中率计算

假设一分钟 1,000 次相同类型展示查询，900 次命中，100 次未命中且各查一次数据库。理想情况下数据库这部分查询从 1,000 次降到 100 次，但还新增了 Redis 查询和回填。真实系统可能有并发回源、重试或多条 SQL，不能直接承诺总数据库负载降低 90%。

商品不存在，能不能缓存？

如果一个不存在的编号被反复请求，每次都查库可能浪费资源。有些系统短暂缓存“不存在”结果，但要考虑该商品稍后创建、权限差异和恶意请求带来的大量键。不能把缓存错误和真正不存在混为一谈。

数据库暂时不可用时，也不能顺手缓存成“商品不存在”，否则故障恢复后用户仍可能拿到错误结果。

价格改了，缓存还没改：并发与一致性

店主把价格从 18 元改成 20 元。数据库已更新，但 Redis 里还是 18 元。旧值什么时候消失，顾客下单按哪个价格结算？这不是 Redis 自己知道的业务问题，需要程序定义。

展示与交易要分清

商品页可以在明确范围内允许短暂旧展示，但提交订单时应按可信业务规则重新确认价格、库存与优惠，并把最终金额告诉顾客。不能把客户端传来的价格或未经验证的缓存展示值直接当成扣款依据。

更新数据库，再删除缓存，也不是魔法

一种常见策略是先更新数据库，再删除相关缓存，让后续读取重新填充。但删除失败、并发读取回填旧值、多个相关键或异步更新，仍会产生复杂情况。简单口诀不能替代对时间顺序的分析。

一种需要分析的并发情况：
读取者先读到旧记录，准备回填缓存；
写入者提交新值并删除缓存；
读取者随后把旧记录写回缓存。
结果：旧值可能暂时重新出现。

可按业务要求采用版本信息、合理过期、串行化某些更新、可靠失效事件等方式，具体方案有复杂度和性能代价。对于要求非常强的新鲜度的操作，最简单可靠的选择可能是不使用这层展示缓存。

热门键一起失效怎么办？

大量请求同时发现没有缓存，可能一起查数据库。热点回源会把原本被缓存遮住的压力突然释放。按场景可以合并同一键的并发加载、分散过期时间、限制回源并发或预热热点，但实现中仍需处理锁超时、失败和旧数据。

缓存服务器不可用时直接让全部请求回数据库，也可能把数据库压垮。降级不是简单的一个 if：要考虑限流、可接受旧值、明确失败以及数据库余量。

选本机缓存还是 Redis，以及怎样保住系统

方式好处需要承担
程序本机内存缓存少一次网络访问，组件简单每实例一份、更新不一致、重启丢失、占程序内存
共享 Redis多个程序访问共同数据，管理更集中网络与服务依赖、内存费用、容量与故障设计
继续优化数据库，不加缓存数据路径简单，一致性更好理解重复查询仍消耗数据库资源

托管 Redis 类服务和自建 Redis 的运维责任也不同。具体产品版本、复制、持久化和计费方式应核对，不能因名字类似就假设恢复行为一样。

内存满了会发生什么？

缓存需要容量上限和淘汰策略。淘汰是容量压力下移除某些内容，和按时间过期不同。采用哪种策略、哪些键可能被移除，会影响命中率与回源。大键还可能影响网络和处理延迟，不能只数键的数量。

即使 Redis 配置了持久化，也不能因此把缓存当数据库备份。它保存的可能只是部分展示结果，结构和更新策略也不等于完整业务记录。

如何证明值得加入？

看命中率、回源量、数据库压力、顾客响应时间和错误率；同时观察缓存内存、淘汰、超时及缓存故障时数据库能否承受。要区分单个热点很快与整体业务真正改善。

故障演练的目标

在隔离环境模拟缓存不可用，观察程序是否无限重试、数据库连接是否暴涨、用户是否得到清楚结果。让系统能在缓存失效时有边界地退化，比只在缓存正常时跑出高数字更重要。

这一章新增的是共享的快取服务和一组读取规则。它不代替入口，不替程序选择机器，也不接管事务。程序先问缓存再问数据库的顺序，让重复工作减少，同时把新鲜度与失效处理变成必须面对的成本。
