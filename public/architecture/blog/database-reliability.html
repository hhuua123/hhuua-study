主库忙、机器坏、数据误删：三种问题不能用一份副本解决

虚构小店的教学场景。规模、耗时和算例不是生产性能承诺；技术方案均需按实际部署核验。

  1. 先分开三个业务要求
  2. 复制怎样影响读取：刚下单为什么可能查不到
  3. 主库失联之后：切换、重连和不确定的写入
  4. 备份不是完成按钮：恢复才是验收

先分开三个业务要求

运营要统计半年订单，数据库读取压力升高；店主要求数据库机器坏了还能尽快接单；另一位同事担心误删商品。这三个要求都像“再弄一份数据”，却对应不同机制。先分清它们，否则很容易买了副本，却以为所有风险都已覆盖。

要求一：让部分读取不再挤占主库

主库是本例接受关键写入的数据库。只读副本接收它的变化，供部分查询使用。副本适合允许一定延迟的读取，例如某些统计或列表。它不能自动增加主库写入能力，也不保证刚提交的订单立刻可见。

要求二：机器出问题时有人接替

备用实例为故障接替准备数据和运行能力。是否同步复制、是否可读、切换方式和等待时间，取决于产品及部署模式。比如托管产品中的“多可用区实例”与“多可用区集群”可能有不同读写与备用角色，不能只看到名字类似就套同一张图。

要求三：找回过去某个正确状态

备份保存可用于恢复的数据副本或恢复所需材料。误删除可能快速复制到在线副本和备用，所以在线复制不能代替独立备份。备份是否完整、保留多久、能否恢复到需要的时间点，都要验证。

升级主库规格可以改善某些资源压力，但不能消除机器故障或误操作。反过来，副本和备份也不能修复一个本身极低效的查询。容量与可靠性需要分别论证。

复制怎样影响读取：刚下单为什么可能查不到

顾客创建订单后立即打开确认页。主库已经提交，副本还没追上。若程序随意把读取分给副本，就可能回答“没有这笔订单”。数据并不一定丢了，可能只是读取位置不符合业务的新鲜度要求。

复制是搬运变化，不是每次都完整复制数据库

数据库通常记录或传递某种变更信息，让副本重放或应用变化；具体机制因数据库和产品而异。异步复制允许主库不等副本全部追上就继续，因此会出现延迟。延迟受写入量、网络、资源和副本执行能力等影响。

同步或半同步等机制对确认条件有不同规定，不能只用“同步”两个字承诺绝对无数据损失或零延迟。选具体方案时，要看故障模型和确认语义。

读写分离不只是把 SELECT 全部送走

读取也有不同一致性要求：刚写后读、库存确认、权限变更可能要求更严格；历史趋势报表可能能容忍延迟。事务中读取与写入的关系也不能随意拆到不同实例。应按业务场景制定策略，再由应用或适当代理实施。

副本落后时可以暂停部分读取分流、提示数据截至时间或按规则回主库，但回主库会增加压力，必须有容量预算。副本不是不需要监控的免费读能力。

主库失联之后：切换、重连和不确定的写入

机器或网络故障后，系统要先判断是否真的不可用，再决定是否切换。错误判断可能带来更严重问题：如果原主库仍接受写入，新主库也接受写入，就可能出现两个地方各写一份的冲突。高可用方案需要限制旧主继续写入等保护机制，不能只是把另一台机器改名为主库。

切换期间顾客会看到什么？

已有连接可能断开，新的地址解析或连接建立可能需要更新。程序要有合理超时、重连与有限重试；某些请求会失败，不能承诺所有切换完全无感。即使托管服务管理了切换，应用也要正确处理连接变化。

写入超时尤其要谨慎：数据库可能已经提交，只是响应没回来。唯一业务编号与结果核查仍然重要，不能因为换了数据库就重新生成一笔订单。

两项业务问题比配置名字更重要

第一，最多能接受停多久；第二，最多能接受丢失多长时间内的数据。工程上常用 RTO 表示恢复时间目标，用 RPO 表示可接受的数据恢复点差距。它们是目标，不是写在方案上就自动实现的保证。

假设业务说“最多停十分钟，最多丢一小时数据”，和“几乎不能丢已确认订单”需要不同设计。即使备份每小时一次，恢复过程也可能很长；备份频率不等于恢复用时。所有数字都应通过实际演练验证。

故障接替测试应包含什么？

在受控环境测试连接恢复、读写正确性、重复订单防护、监控告警和人员处置。看服务恢复后是否存在数据缺口，而不只是新主库显示运行中。还要核对旧实例恢复之后如何重新加入，避免再次出现角色混乱。

备份不是完成按钮：恢复才是验收

备份在哪里，谁能删除？

备份只放在同一块磁盘，无法防止那块磁盘损坏；备份账号与业务账号都拥有完全删除权限，也可能被同一错误影响。根据业务需要设计存放位置、保留期、访问权限和恢复流程。不同地区与故障域的选择还涉及成本和合规要求。

快照、逻辑导出和按时间点恢复材料有不同用途、速度与限制。不能仅看到“备份成功”就知道能恢复到哪一秒、需要多久、是否包含全部依赖。

恢复不是简单覆盖生产数据库

常见验证方式是恢复到独立环境，核查表、关键记录、应用兼容与权限，再制定实际切换或数据修复方案。误删后直接覆盖当前库，可能把之后正常产生的订单也抹掉；恢复历史数据与保护后续业务需要一起考虑。

误删与历史恢复独立备份、版本与时间点恢复保存费用、恢复时间和核验流程

托管数据库能减少部分维护工作，但套餐、引擎和部署模式差异很大；自建控制力更高，也要求更强值守能力。应选择团队能长期运行并演练的方案，不只比较正常情况下的月费用。

这一阶段之后，程序按业务选择数据目标；复制与备份在旁路进行。图上不能把副本、备用和备份画成每笔订单的必经步骤。正确理解这点，才能解释为什么有了三份数据，仍然可能发生某些读取延迟或恢复问题。
