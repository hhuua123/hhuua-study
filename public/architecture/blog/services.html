商品与订单分开发布：服务边界比机器数量更重要

虚构小店的教学场景。规模、耗时和算例不是生产性能承诺；技术方案均需按实际部署核验。

  1. 先把代码分清，不要急着把网络连满
  2. 入口先选服务，再选实例：两次决定不能混为一谈
  3. 一次本地调用变成网络调用，会多出什么失败
  4. 拆分的收益如何验收，什么时候先别拆

先把代码分清，不要急着把网络连满

商品团队每周改展示和筛选，订单团队希望稳定。原来一个程序一起构建、一起测试、一起发布；商品的小改动也需要订单团队配合。升级服务器解决不了发布节奏，复制更多相同程序也不会让职责自动独立。

单体程序不是贬义词

一个部署单元可以包含清晰模块，承接很大的业务。模块是代码中的职责划分，服务则是独立运行并通过接口通信的边界。先把商品、订单、通知等模块的责任与数据访问分清，常常比立即拆机器更有效。

拆成服务需要明确负责人、接口契约、版本兼容和故障处理。如果团队很小，所有服务仍一起修改和发布，只是多了网络连接，可能得到更难维护的“分布式大程序”。

选哪一块先拆？

优先考虑职责清楚、调用关系可理解、能够独立验证的部分。可以通过入口逐步把某类请求转给新服务，其余仍留在原程序。逐步替换比一次改掉所有代码更容易控制风险，但要管理新旧数据和路由的一致性。

不按“每个名词一个服务”机械拆分。过细边界会增加网络往返和协作成本；过粗边界仍绑在一起。判断依据是业务变化、责任和独立发布收益，而不是图上节点数量。

入口先选服务，再选实例：两次决定不能混为一谈

小林查看商品时访问 /api/products/123，点击下单时发送 /api/orders。入口按配置把不同请求交给不同服务组，然后在该组的健康实例中选择目标。这并不意味着一次商品查询必须经过订单服务。

下单为什么可能需要商品信息？

订单要确认商品、价格等信息，但不应随意修改商品服务的数据表。可以通过约定接口取得必要数据，或根据明确业务机制使用同步后的数据。下单时保存交易需要的价格和商品快照，避免后来商品名称变化让历史订单失去含义。

哪些信息必须即时确认、哪些可以稍旧，是业务规则。服务拆分后，数据往往不在同一简单事务边界里，这需要在设计接口时就考虑，而不是上线后才发现订单与库存可能不同步。

接口契约是什么？

约定输入字段、返回字段、状态、权限、错误含义与兼容方式，就是接口契约。调用方不能只靠猜测“200 就一定创建订单”。某个字段移除或含义变化，可能让旧版本调用方失败，因此发布要考虑新旧版本并存。

HTTP/JSON 常见且易观察；某些内部系统使用 gRPC 等方式获得类型约定与不同通信特性；异步事件适合不需要立即结果的通知。协议选择应服务于业务与团队能力，不是越新越好。

一次本地调用变成网络调用，会多出什么失败

超时只说明你没等到确定结果

订单服务调用另一个服务，对方可能根本没收到，也可能已经完成只是响应丢了。重试之前要看操作是否安全重复，使用业务请求编号与结果查询。把超时等同于“没有执行”会产生重复扣减或重复订单。

两个数据库不自动共享一个事务

商品或库存服务完成预留，订单服务随后失败，可能需要取消预留。补偿是按业务规则执行的反向或修复动作，不一定等于数据库回滚。钱已经扣走时退款也有自己的状态与失败可能。

有的流程由一个协调者按步骤推进和补偿，常被称为 Saga 一类模式；有的采用事件协作。先画清楚每一步成功、失败和未知时怎么处理，再选择实现。不能因为用了消息队列就断言跨服务一致性自动解决。

一段需要明确的订单状态

待确认 → 已预留 → 已创建；失败可能转为取消中 → 已取消。状态必须对顾客与运营可解释，后台补偿失败也要有人排查。实际业务可采用不同状态，本例只说明“成功/失败”两个值可能不够。

调用链越长，越要有等待预算

如果入口等程序，程序等商品，商品又等其他服务，任何一段慢都会传导。并行调用可能减少等待，但会增加并发和部分失败处理。总超时、重试、降级、缓存和隔离需要协调，不能每个团队各设一个很长超时就算完成。

通过追踪标识把一次操作关联起来，记录每段等待与业务结果。调用图中应区分同步等待和异步事件，不能把队列里的后续工作画成前台必经步骤。

拆分的收益如何验收，什么时候先别拆

收益不只看吞吐

观察商品与订单是否真能独立发布、故障影响是否缩小、局部扩容是否节省资源、团队责任是否更清晰。也要记录接口失败、跨服务等待、数据对账和运维成本。独立服务更多但每次仍必须全体发版，说明边界可能没划好。

技术选择的几种方向

方向收益代价
模块化单体部署简单，本地调用和事务易理解发布与整体扩容仍有耦合
少量独立服务职责与发布更独立网络、接口兼容、数据归属与恢复
更细服务与统一治理平台可为复杂组织提供更细控制平台、追踪、安全、成本及长期值守要求高

入口可用云 ALB、Nginx 或具备 API 管理能力的网关。鉴权、限流、路由等能力是否集中，依组织和产品需要；网关不能替业务服务判断每笔订单的归属与交易规则。

服务间加密、重试和观测可以先由应用库和基础设施实现。服务网格与边车不是拆服务后的必选套餐，后面的 Kubernetes 专题会把它们作为可选方案讲清。

这一章的关键变化

从一个部署单元的内部函数调用，变成明确接口与事件连接的多个服务；入口按业务路径分流，数据按归属管理。机器变大解决容量，服务拆分解决的是另一类边界与协作问题。只有收益超过新增失败与维护成本，才值得走这一步。
