完整专题

第一阶段 · 专题讲义

顾客点开一件商品，一台服务器里究竟忙了什么？

我们开一家只有几十种商品的小店。顾客小林打开“手作杯”的商品页，看到名称、价格、库存和图片。先不引入缓存、队列或集群，只租一台云服务器，把整件事从头做完。

今天的假设，不是生产容量标准

一台 Linux 云服务器：2 个虚拟处理器核心、4 GiB 内存、80 GB 固态磁盘、公网出口上限 10 Mbps。页面和程序放本机，数据库也在本机。用这些数字算清楚资源怎么消耗，不据此承诺能承受多少顾客。

先看最终画面：不是“服务器”一个东西在干活

服务器是一台计算机，可以同时运行许多程序。云服务器是云厂商提供的一台虚拟计算机；你获得处理器、内存、磁盘和网络等资源，具体物理资源如何分配由云产品决定。下面选一套具体实现：Nginx 做网站入口，Python 业务程序处理商品规则，MySQL 管理商品和订单记录，Linux 操作系统负责协调资源。换成别的语言或数据库，分工仍然可以类似。

小林的浏览器显示页面 · 发送请求 · 下载图片
⇅ 公网：请求过去，响应回来
一台云服务器的边界

Nginx · 网站入口

监听 443 端口，处理 HTTPS；静态文件直接读取，业务请求转给程序。

业务程序 · 小店规则

解析商品编号，判断能否展示，查询数据库，整理返回数据。

MySQL · 业务记录

按查询条件找商品，保存订单；使用自己的内存和磁盘文件。

文件目录 · 图片与页面

保存 HTML、脚本、样式和图片。目录是存放位置，不是另一个服务程序。

Linux 操作系统：安排进程使用 CPU、管理内存、访问磁盘、收发网络数据
CPU 算事情内存放正在用的东西磁盘长期保存带宽搬运数据

第一幕：输入网址后，浏览器先找谁？

小林访问 https://shop.example.com/products/123。浏览器需要先知道这个域名对应哪个网络地址，这个查询过程叫 DNS，像查通讯录。结果可能已经被缓存，不一定每次重新询问。随后浏览器连接服务器，并建立 HTTPS 加密通信；它会验证网站证书，确认连接的身份符合访问的域名。

为了方便理解，这里采用常见的 HTTPS 入口模型。连接建立成功后，浏览器发送请求。已有连接往往能复用，因此不能认为每个图片请求都必须重新完整查域名、握手。公网路由、协议版本、网络状况都可能改变实际耗时。

小林想要什么GET /products/123域名 shop.example.com · 商品编号 123
GET：读取一个资源
/products/123：要看的页面路径
Host：访问哪个网站
Cookie：可能携带登录凭证
Accept：希望收到的内容类型

这些说明不等于数据库指令。浏览器说“我要这个页面”，服务器决定怎样完成。我们假设此路径先返回商品页的 HTML 外壳，页面里的脚本再请求商品数据。这是一种常见实现；也可以由服务器一次生成包含商品数据的 HTML，不能把两者当成唯一标准。

第二幕：入口为什么不直接就是业务程序？

Nginx 是一直运行、等请求到来的入口程序。443 是本例 HTTPS 入口使用的端口，可以理解为网络地址上的一个服务门牌。Nginx 根据配置处理这个网站的请求：页面、样式和图片可以从本机目录读取；以 /api/ 开头的请求转交业务程序。

转交叫“反向代理”：顾客面对统一入口，入口代他找后面的程序。本例业务程序只监听本机地址 127.0.0.1:8000，数据库只接受本机授权连接。这样顾客不必、也不应拿到数据库账号。入口处理证书、连接和转发，业务程序集中处理小店规则。小项目也可以让应用服务器直接承担入口，但证书、静态文件和对外暴露等职责仍然需要有人完成。

路由配置的示意，不是可直接上线的完整配置

/api/* → 本机业务程序
/images/* → 本机图片目录
/products/* → 商品页 HTML

入口不因为看见商品编号 123 就知道价格，也不因为转发了 Cookie 就自动完成顾客授权。文件目录、路径匹配、超时和安全权限都要配置正确。

第三幕：浏览器拿到页面，又发起数据请求

HTML 描述页面结构，CSS 决定外观，JavaScript 脚本可以负责请求数据与更新页面。它们到达浏览器后，由小林的设备解析和执行，并不是服务器替浏览器画好每一个像素。假设页面脚本请求 GET /api/products/123，Nginx 按规则把它交给本机业务程序。

程序读取编号，检查格式、商品是否允许公开展示；如果是私人订单页，还必须验证登录身份与订单归属。它通过数据库连接发送参数化查询，例如“按编号查商品名称、展示价格和图片位置”。参数化意味着把输入的数据与查询结构分开处理，避免直接把用户输入拼成数据库指令。

示意数据：
商品编号：123
名称：手作杯
展示价格：18 元
图片位置：/images/cup-123.jpg

查询意图：找到编号为 123、允许展示的商品。
这只是说明业务，不是完整的数据库表设计。

MySQL 根据查询条件和索引等选择查找方式。索引像账本目录，可能减少要检查的记录；并不是每次查询都必须从磁盘完整读一遍，因为数据库和操作系统都可能已把常用数据放在内存。数据库返回记录，业务程序把记录整理成 JSON——一种用字段名和值表达数据的格式，再交给 Nginx 返回浏览器。

这一条数据请求的完整往返

  1. 浏览器 → Nginx：请求商品 123，携带必要请求头。
  2. Nginx → 业务程序：按 /api/ 路由转发；本例发生在同一机器内部。
  3. 业务程序 → MySQL：发送带参数的查询，等待结果。
  4. MySQL → 业务程序：返回商品记录、空结果或错误。
  5. 业务程序 → Nginx：生成响应状态、内容类型和 JSON 数据。
  6. Nginx → 浏览器：发送响应，浏览器把名称和价格显示出来。

数据库不会把网页直接发给小林；它回答的是业务程序。没有找到商品时程序可以返回 404 等适当结果，内部查询失败则需要记录原因并返回合适错误，不能把数据库密码和内部堆栈交给顾客。

第四幕：图片为什么又是另一条路？

浏览器根据图片地址请求 /images/cup-123.jpg。入口按规则读取本机文件并把图片字节送回。对于这条简单静态图片请求，业务程序和数据库都可以不参与。因此一张商品页不是“一次请求”：它可能包含 HTML、样式、脚本、商品数据和多张图片；浏览器还可能复用缓存，或并行下载多个资源。

浏览器→Nginx→本机图片文件
浏览器←Nginx←图片字节

这解释了为什么“每天一万访客”不足以选择配置：每人只打开一个小页面，和每人连续下载几十张大图，资源消耗完全不同。平均请求数也不能代表活动时同一秒到来的峰值。

机器里面的四种资源，到底分别忙什么？

CPU：真正执行指令的人

程序判断规则、数据库处理查询、HTTPS 加解密、图片压缩都需要计算。CPU 核心数像可同时工作的计算岗位，但程序能否利用多个核心，取决于实现和并发方式。虚拟核心也不等同于独占的一颗物理处理器。

例子：假设每个业务请求实际消耗 20 毫秒 CPU，100 次/秒就需要约 2 个核心秒/秒，理论上已吃满两个核心；还没给数据库、入口和操作系统留余量。这是算术示例，不是压测结论。

不够用时：计算任务排队，响应变慢。先区分程序计算、数据库查询和后台任务；优化或增加核心可能有效，但网络等待长不意味着 CPU 必然忙。单个线程成为瓶颈时，增加核心也未必自动改善。

内存：工作台，不是永久仓库

运行中的程序代码和数据、数据库缓冲、连接缓冲、操作系统文件缓存都占内存。进程是操作系统管理的运行中程序实例；同一机器可以有多个业务进程，每份可能占用自己的内存。

例子：4 GiB 内存中，假设系统及入口 0.7 GiB、业务进程合计 1 GiB、数据库 1.5 GiB，已用约 3.2 GiB，剩余并不是都能放心分配给新请求。流量突增、查询或文件上传可能增加临时占用。

不够用时：系统可能回收缓存、使用磁盘交换空间，或终止进程；具体行为依系统配置。交换空间比内存慢，不能当免费内存。应检查进程、连接数与泄漏，区分可回收缓存和真正持续增长的占用。

磁盘：容量与忙碌程度是两回事

系统、程序文件、数据库文件、图片和日志都需要磁盘空间。空间还有很多，不代表磁盘能及时完成大量读写；吞吐量是每秒搬多少数据，IOPS 是每秒能完成多少次读写操作，延迟是一次操作等多久。

例子：80 GB 中，系统与程序 12 GB、数据库 18 GB、图片 30 GB、日志 10 GB，已占 70 GB。每天净增长 1 GB，粗算约十天就耗尽剩余空间，而且运行和维护还需要余量。

不够用时：写订单或日志可能失败；即使空间没满，大量随机读写也可能让数据库等待。扩容量、换更快的盘、减少扫描和管理日志分别解决不同问题。删除不明数据库文件不是扩容办法。

带宽：出入口每秒能搬多少

带宽是数据传输的速率上限，不是“每月能用多少流量”。流量是累计传输量。带宽通常用 Mbps（每秒百万位），文件大小常用 MB（百万字节）；一个字节有八个位，所以数值不能直接混用。

例子：10 Mbps 理想换算约 1.25 MB/s。每个页面下载总共 2 MB，不考虑缓存和协议开销，单个页面仅传输就约需 1.6 秒；十个顾客同时下载这批共 20 MB 的内容，共享出口至少约需 16 秒才能全部送完。不是每人都独享 10 Mbps。

不够用时：图片下载拖长，CPU 可能仍很闲。压缩图片、浏览器缓存、提高出口能力或以后引入 CDN 都可能有效。更大 CPU 不能直接把有限的网口变宽；真实时间还受线路、距离和客户端影响。

做一次小实验：同样是“页面慢”，该改哪里？

点开现场记录，先猜原因，再看分析。这些是故意简化的假设，真实排查还要用测量确认。

现场 A：CPU 很闲，图片下载却很慢

如果出口已接近限制，应先看图片体积、缓存与网络；升级 CPU 不是针对性方案。浏览器网络面板能帮助区分等待服务器与实际下载时间，服务端出口指标可交叉验证。

现场 B：数据库查询很慢，磁盘空间还有一半

容量充足不代表读写快。检查查询扫描量、索引、磁盘读写延迟及内存缓存情况。增加硬盘容量未必改善大量随机读写，也可能根本是查询本身需要优化。

现场 C：低峰正常，一到高峰程序就被重启

检查是否发生内存不足、程序异常或健康检查失败。更多连接和工作进程可能增加内存占用。先看系统事件与进程记录，再决定限制并发、修复泄漏或扩内存。

现场 D：换成大机器后，发布仍然全站中断

这是可用性与发布方式的问题。机器再大，只运行一份程序时，停止它仍会中断服务。以后可能需要多份程序、统一入口和稳妥切流量；不是今天就必须把全部架构加上。

为什么几个程序能同时在一台机器上运行？

操作系统安排不同进程轮流或并行使用 CPU，管理各自的内存，并协调磁盘和网络。当程序等待数据库或网络时，CPU 可以执行其他就绪任务。一个请求等待了 100 毫秒，不等于 CPU 为它连续算了 100 毫秒。

同时处理请求的方式有多进程、多线程和事件驱动等。先理解共同目标：一个顾客在等结果时，不要让所有顾客都无谓停住。但并发不是越大越好；连接、缓冲和执行中的任务会占资源。无限接单可能把有限内存和数据库连接耗尽，所以需要设置合理上限、超时并通过压测验证。

如果今天真要选技术，我会怎样比较？

云服务器或托管应用云服务器控制力强，但系统更新、部署和监控需要维护。托管应用平台能代管部分工作，却有运行方式、配置和费用方面的限制。先选团队能稳定维护的方案。
Nginx / Caddy / 应用自带入口前两者可集中处理代理和静态内容等入口工作，各自配置与证书管理方式不同。应用直接对外较少组件，但必须确认它的生产部署方式、连接处理和安全配置，不能把开发调试服务器当成完整生产方案。
Python / Node.js / Java 等都可以实现网店规则；生态、人员熟悉程度、部署和资源使用不同。语言名字不能单独决定网站能承受多少流量，数据库访问和业务设计往往同样关键。
MySQL / PostgreSQL / 更轻量存储前两者适合需要结构化查询和事务的业务，但要维护连接、备份和权限。简单小应用也可能用嵌入式数据库，不过并发写入、部署方式与恢复需求必须单独评估，不应只看安装方便。

这一阶段真正应该做好的事

让每个程序职责清楚，知道哪些端口对外、哪些只供本机或内网使用；给数据库和文件设置备份，并验证能恢复。备份存在同一块磁盘上，不能防止这块磁盘损坏。保存基本运行指标和错误日志，控制日志增长，管理证书与系统更新。

当资源确实不足而单机仍符合业务可靠性要求时，升级服务器可以是合理选择。等到出现文件共享、故障接替、资源隔离或重复查询等明确问题，再引入下一种组件。本阶段的目标不是把架构做大，而是能准确说出：这一条请求谁接、谁算、谁存、谁返回，以及哪一种资源正在限制它。

请试着解释给第一次接触网站的人听

为什么图片请求可以不查数据库？为什么 100 毫秒的响应不等于 100 毫秒的 CPU 工作？为什么磁盘没满也会慢？为什么更强的服务器仍可能一停全停？能用今天的请求故事回答，就真的理解了这台机器。
